# AILink 智链 · 产品与技术架构

> 版本：v1.0（2026-11-05）  
> 定位：从可交互原型到可收款、可发信、可运营的生产系统。

---

## 一、当前原型是什么

当前交付是一个**纯前端单页应用**：

- `index.html` + 原生 CSS / JavaScript，无构建步骤；
- `assets/hangzhou-ai.js`、`assets/shenzhen-ai.js` 分别内置 42 家杭州、42 家深圳 AI 企业公开资料；`assets/hangzhou-batch2.js` 内置 100 家杭州 Batch 02 待核验企业；`assets/shenzhen-batch2.js` 内置 100 家深圳 Batch 02 待核验企业；`assets/data.js` 将其映射为项目库记录并合并其余演示数据（共 366 项目 / 36 资金 / 48 人才）；
- 路由、筛选、详情、会员门禁、模拟支付、模拟发信全部在浏览器完成；
- 登录状态、收藏、活动记录、额度存在 `localStorage`；
- 无后端、无真实支付、无真实 SMTP、无真实个人信息。

它的作用是先把**信息架构、会员价值、计费方式、邮件工作流**跑通，用于产品评审、种子用户测试和融资演示。

生产化要替换的不是页面，而是页面背后的四层：**身份与权限、数据与检索、支付与额度、邮件与合规**。

## 二、生产系统目标

### 功能目标

1. 三类数据库的采集、清洗、核验、发布与更新；
2. 访客 / 专业 / 团队 / 机构四档会员与字段级权限；
3. 微信 / 支付宝 / 对公支付，订单、发票、退款、额度账本；
4. 按量计费的邮件活动：人群、模板、AI 起草、队列、频控、退订、Webhook、报告；
5. 数据认领、纠错、推荐、删除 / 撤回；
6. 运营后台：导入、审核、质量看板、供应商管理。

### 非功能目标

| 维度 | 目标 |
| --- | --- |
| 可用性 | 99.9% |
| 首屏 | < 2.5s（4G） |
| 搜索 | P95 < 300ms |
| 数据规模 | 10 万项目 / 1 万资金 / 10 万人才 |
| 邮件 | 单活动 5 万收件人，队列可重试 |
| 安全 | RBAC、字段级权限、审计日志、加密 |
| 合规 | PIPL / 数据安全法 / 邮件管理办法 / ICP |

## 五、字段级权限

这是会员产品的核心，不是前端隐藏。

### 5.1 角色

| 角色 | 权限 |
| --- | --- |
| visitor | 摘要、脱敏字段、无联系方式 |
| member_pro | 完整档案、联系方式、导出 200 条 / 月 |
| member_team | 团队共享、导出 1,000 条 / 月 |
| org_admin | 席位、账单、团队标签、导出审计 |
| data_ops | 数据导入、审核、发布、撤回 |
| super_admin | 全部 + 供应商与合规配置 |

### 5.2 返回策略

API 永远不返回前端“再隐藏”的敏感字段。根据角色组装 DTO：

```ts
function toProjectDTO(project, viewer) {
  const base = { id, name, city, sectors, stage, description };
  if (!viewer.isMember) {
    return { ...base, contact: null, funding: null, founder: null };
  }
  return {
    ...base,
    funding: project.funding,
    founder: project.founder,
    contact: decryptContact(project.contact) // 单独授权 + 审计
  };
}
```

- 联系方式加密存储（KMS / pgcrypto）；
- 每次查看 / 复制 / 导出写访问日志；
- 导出走异步任务，生成带水印的 CSV，链接 24 小时过期；
- 会员协议禁止转售；异常批量导出触发风控。

## 七、支付与额度

### 7.1 订阅

1. 前端选套餐 → 创建 `order`（pending）；
2. 调起微信 / 支付宝；
3. 支付回调 → 验签 → 幂等检查 → `order=paid`；
4. 创建 / 续期 `subscription`；
5. 写 `credit_ledger` 加月度额度；
6. 异步开票；
7. 前端轮询 / WebSocket 更新权益。

### 7.2 加油包

- 独立订单，支付成功后加额度；
- 额度有有效期（当前周期 / 12 个月），过期前 7 天提醒；
- 退款策略：未使用额度可退，已使用按比例扣减；写进会员协议。

### 7.3 幂等与对账

- `idempotency_key = provider + provider_order_id`；
- 每日对账：支付平台账单 vs `orders`；
- 额度账本每日快照，异常告警；
- 禁止前端传额度，全部服务端计算。

## 八、邮件系统

### 8.1 发送流程

```text
选择人群 → 服务端重算收件人 → 排除 suppressions / 退信 / 重复
→ 渲染变量 → 预检（空变量、敏感词、链接）
→ 创建 campaign + campaign_recipients（queued）
→ BullMQ 分批入队（每批 200）
→ 发信服务商 API
→ Webhook 回写 delivered / bounced / opened / clicked
→ 报告聚合
```

### 8.2 频控

- 同一邮箱 30 天 ≤ 2 封（可配置）；
- 同一 org 每日上限；
- 新域名预热：第 1 周 50 封 / 天，逐步提升；
- 退信率 > 5% 自动暂停；
- 投诉率 > 0.1% 自动停发并告警。

### 8.3 发信域名

- 独立子域名，如 `mail.ailink.cn`；
- SPF、DKIM、DMARC（p=quarantine）；
- 自定义 Return-Path；
- 预热与信誉监控（Google Postmaster / Microsoft SNDS）；
- 国内使用阿里云邮件推送 / 腾讯云 SES，海外用 SendGrid / Resend。

### 8.4 退订

- 每封带 one-click unsubscribe（RFC 8058）；
- `List-Unsubscribe` 头；
- 退订页不需要登录；
- 退订后立即写入 `suppressions`，所有队列实时排除；
- 事务性邮件（如验证码）与营销邮件分开域名 / 子账号。

### 8.5 AI 起草

- 服务端拼 prompt：人群画像 + 发件人 + 目标 + 品牌语气 + 合规约束；
- 输出版本化，保留 prompt / 模型 / 时间，便于审计；
- 敏感词与虚假承诺过滤；
- 变量替换后再做一次事实检查（公司名、联系人、阶段）；
- 不把完整联系人列表发给模型；只发必要字段。

## 九、数据导入与运营后台

### 9.1 导入流程

1. 上传 CSV / Excel；
2. 字段映射（自动识别 + 手动调整）；
3. 预览前 20 行；
4. 校验：必填、格式、枚举、重复、敏感字段；
5. 进入 `review_queue`；
6. 运营审核 / 批量通过；
7. 发布到主库 + 重建搜索索引；
8. 记录导入批次、操作人、来源、授权。

### 9.2 质量看板

- 各城市 / 赛道的覆盖量；
- 字段完整率；
- 核验率、退信率、失效率；
- 待审核队列时长；
- 会员纠错与认领量；
- 供应商数据准确率对比。

### 9.3 认领与纠错

- 企业认领：域名邮箱验证 + 营业执照（可选）；
- 人才认领：手机 / 邮箱验证；
- 纠错：会员提交 → 运营审核 → 变更日志；
- 删除：48 小时内处理，保留最小审计记录。

## 十、安全与合规

### 10.1 技术安全

- 全站 HTTPS / HSTS；
- 密码 Argon2id / bcrypt；
- 登录限流、验证码、异常登录告警；
- RBAC + 字段级权限；
- 联系方式加密（KMS）；
- 导出文件加密 / 水印 / 过期链接；
- SQL 注入、XSS、CSRF、SSRF 防护；
- 依赖扫描、渗透测试、备份演练；
- 审计日志不可篡改（append-only）。

### 10.2 合规

- 隐私政策、会员协议、DPA、Cookie 政策；
- 同意记录（时间、版本、IP、范围）；
- 数据来源与授权链存档；
- 删除 / 更正 / 撤回通道；
- 供应商尽调与年度复审；
- ICP 备案、等保（按规模）；
- 数据出境评估（如使用海外服务）。

### 10.3 邮件合规

- 只发有合法联系依据的对象；
- 真实发件人、真实主题；
- 退订、频控、投诉处理；
- 保留发送记录 ≥ 3 年；
- 不购买名单、不伪造回复、不诱导转发。

## 十一、可观测性与运维

- **日志**：结构化 JSON，集中采集，PII 脱敏；
- **指标**：QPS、P95、错误率、队列积压、发信成功率、退信率；
- **追踪**：OpenTelemetry，关键链路（搜索、详情、支付、发信）；
- **告警**：支付回调失败、额度异常、退信率、队列堆积、数据导入失败；
- **备份**：PostgreSQL 每日全量 + 持续归档；对象存储版本化；
- **恢复**：RPO < 15 分钟，RTO < 2 小时；
- **发布**：预览环境 + 灰度 + 回滚；
- **权限**：生产数据最小权限，操作留痕。

## 十三、验收标准

- [ ] 会员能注册、升级、支付、开票、退款；
- [ ] 访客无法通过 API 拿到联系方式；
- [ ] 搜索 P95 < 300ms（10 万级数据）；
- [ ] CSV 导入 1 万行 < 2 分钟，错误可定位；
- [ ] 邮件活动 1 万收件人可暂停 / 续发 / 重试；
- [ ] 退订 1 分钟内生效；
- [ ] 额度账本与支付订单每日对账一致；
- [ ] 删除请求 48 小时内全链路生效；
- [ ] 审计日志可查“谁在什么时候看了哪条联系方式”；
- [ ] 移动端 390px 无横向滚动；
- [ ] 关键流程 E2E 自动化覆盖。

## 十五、从原型迁移的步骤

1. 保留现有视觉与交互，作为前端设计基准；
2. 把 `assets/data.js` 导出为 CSV / JSON，导入 PostgreSQL；
3. 用真实 API 替换 `app.js` 中的 `D` 数据源；
4. 把 `localStorage` 用户替换为服务端 session；
5. 把模拟支付替换为订单 + 回调；
6. 把模拟发送替换为队列 + 邮件服务商；
7. 把前端 `isMember()` 替换为服务端返回的 entitlements；
8. 保留 demo 模式作为销售演示环境（`DEMO_MODE=true`）。

## 十六、明确不做的事

- 不做“全网企业黄页”式的无限扩张；
- 不卖来源不明的个人手机号 / 微信 / 简历；
- 不做绕过平台风控的爬虫；
- 不做“付费就能群发所有人”的邮件工具；
- 不在第一版做复杂 AI Agent 自动成交；
- 不把“数据量”当作唯一 KPI。

先把“杭州 + 深圳 2,000 条 + 100 位付费会员 + 50 次真实对接”跑通，再谈全国。
