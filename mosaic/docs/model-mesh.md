# Mosaic Model Mesh · 多模型编排设计

> 目标：让「所有顶尖模型」对用户表现为**一个稳定、可解释、越来越懂你的模型**。用户不需要选择模型，但随时可以接管。

---

## 1. 为什么需要一层 Mesh

一个 App 的生成不是一次调用，而是一条由 30–80 次模型调用组成的流水线。不同步骤对能力的要求完全不同：

- 澄清问题要**快、便宜、不打断心流**；
- 信息架构要**结构化、长上下文、少幻觉**；
- 首屏代码要**一次成型、组件拆分合理**；
- 高频微调要**便宜到可以试 20 次**；
- 设计评审要**审美判断**，而审美恰恰是单模型最容易同质化的地方。

把整条流水线绑在一个模型上，要么贵得离谱，要么在某个环节明显短板。Mesh 的价值就是：**每个环节都用当时最合适的模型，并且整体成本可控。**

## 2. 能力注册表（Capability Registry）

每个模型在注册表里不是一条「名称 + 价格」，而是一组可查询的能力向量。

```ts
type ModelEntry = {
  id: string;                    // "anthropic/claude-opus-5.5"
  vendor: string;
  family: string;
  releasedAt: string;
  context: number;               // tokens
  modalities: ("text"|"image"|"audio"|"video")[];
  capabilities: {
    reasoning: number;           // 0-100
    codegen: number;
    uiCode: number;              // 界面代码专项
    vision: number;              // 截图理解
    toolUse: number;
    chinese: number;
    longContext: number;
    instruction: number;         // 遵循复杂约束
  };
  pricing: { input: number; output: number; cachedInput?: number; image?: number };
  latency: { ttftP50: number; tpsP50: number };
  limits: { rpm: number; tpm: number; regions?: string[] };
  policy: { dataResidency: string[]; trainsOnData: boolean; exportRestricted?: boolean };
  status: "ga" | "preview" | "restricted" | "deprecated";
  benchmarks: Record<string, number>;  // swebench, terminal, mcpAtlas...
};
```

**维护方式**：

- 每日从供应商 API / 状态页同步可用性与价格；
- 每周从 Artificial Analysis、LMArena、SWE-bench 等公开源更新基准；
- 每日从站内 Run 表更新**采纳率**（人工接受 / 修改 / 拒绝）；
- 任何模型连续 24h 错误率 > 5% 自动降级为备用。

## 3. 任务分类（Task Taxonomy）

路由的最小单位不是「聊天」，而是**任务类型 + 风险等级**。

| 代码 | 任务 | 典型输入 | 典型输出 | 质量门槛 | 成本敏感 |
|---|---|---|---|---|---|
| T01 | intent_parse | 一句话 | 结构化意图 | 中 | 高 |
| T02 | clarify | 意图 + 上下文 | 1–5 个问题 | 高 | 中 |
| T03 | product_plan | 意图 + 约束 | 页面/数据/接口计划 | 高 | 低 |
| T04 | ia_design | 计划 | 导航与流程 | 高 | 低 |
| T05 | visual_direction | 品牌 + 参考 | 3 个 DNA + 首屏 | 高 | 中 |
| T06 | screen_codegen | DNA + 组件规格 | TSX | 极高 | 中 |
| T07 | component_iterate | 选中组件 + 指令 | diff | 高 | 极高 |
| T08 | screenshot_to_code | 截图 | 组件树 + 代码 | 极高 | 中 |
| T09 | design_critique | 界面 + rubric | 问题清单 | 高 | 中 |
| T10 | test_gen | 代码 | 测试 | 高 | 高 |
| T11 | fix_build | 报错 + 代码 | patch | 极高 | 中 |
| T12 | copywriting | 场景 + 语气 | 文案 | 中 | 高 |
| T13 | localize | 文案 + 语言 | 多语言 | 中 | 高 |
| T14 | image_asset | 描述 + 风格 | 图 | 中 | 中 |
| T15 | store_listing | App 信息 | 商店文案/截图 | 中 | 低 |
| T16 | codebase_qa | 大代码库 | 回答/重构 | 高 | 低 |

**风险等级**：

- R0：可自动重试，无需用户确认（T01、T12）。
- R1：展示 diff，用户可撤销（T06、T07）。
- R2：需要显式确认（T03 的架构变更、T10 的删除操作、上架相关）。
- R3：禁止自动执行（支付、隐私、权限、生产数据迁移）。

## 5. 路由策略

### 5.1 四种策略并存

| 策略 | 适用 | 逻辑 |
|---|---|---|
| **Quality-first** | 首屏、架构、上架 | 达到质量阈值中最强；成本只做上限约束 |
| **Balanced**（默认） | 大多数任务 | 质量 55% + 速度 20% + 成本 15% + 稳定性 10% |
| **Cost-first** | 高频微调、批量变体 | 达到最低质量线后选最便宜 |
| **Pinned** | 企业合规、用户手动 | 固定模型/供应商，不自动切换 |

用户可在项目设置里选「省钱 / 平衡 / 最好」，对应三套权重；高级用户可逐任务覆盖。

### 5.2 打分函数

```ts
score(m, task, ctx) =
    0.55 * quality(m, task)        // 站内采纳率 0.6 + 公开基准 0.4
  + 0.20 * speed(m, task)          // 归一化 TTFT 与 TPS
  + 0.15 * cost(m, task)           // 归一化预估成本
  + 0.10 * reliability(m, ctx)     // 近 7 天成功率、限流情况
  - penalties(m, ctx)              // 地域、数据政策、出口限制、上下文超限
```

`quality(m, task)` 的站内部分：

```
采纳率 = 被接受且未大改的 run / 该模型该任务的总 run
```

> 注意：不能只看「用户是否点接受」，还要看「接受后 24h 内是否被再次修改」。后者更能反映真实质量。

### 5.3 选择流程

```
1. 过滤：能力、上下文、地域、数据政策、状态（ga/preview）
2. 粗排：按 quality 取前 4
3. 预估：token 与成本（考虑缓存命中）
4. 精排：按策略打分
5. 预算检查：超预算则降级到「质量达标的最便宜」
6. 生成 fallback chain（同供应商 → 跨供应商 → 自托管）
7. 记录候选与最终选择（用于反事实评估）
```

### 5.4 失败与降级

| 情况 | 动作 |
|---|---|
| 429 / 5xx | 指数退避 2 次 → 切 fallback（目标 < 50ms 决策） |
| 超时（> 30s 无首 token） | 并行启动备用，先到先用，取消另一个 |
| 输出不合 schema | 同模型重试 1 次（temperature 降低）→ 换模型 |
| 代码构建失败 | 把错误喂给 fix_build（升级到更强模型） |
| 内容拒答 | 判断是安全策略还是能力不足；前者提示用户，后者切换模型 |
| 地域限制 | 路由到合规区域的自托管实例 |

**降级不能静默改变语义**：如果从 Fable 5 降到 DeepSeek，UI 要显示「已切换到更快的模型」，并允许重跑。

### 5.5 多模型评审（Consensus）

用于 T05（设计方向）、T09（设计评审）、T15（商店文案）等高价值、低频率的决策。

```
3 个模型并行 → 各自按 rubric 打分（0-5）→ 汇总模型（便宜）做加权合并
                → 若分歧 > 1.5 分，展示分歧点让用户裁决
```

成本约为单模型的 3.2 倍，但只覆盖 < 5% 的调用，对总成本影响 < 15%。

## 6. Prompt Compiler：同一意图，不同模型的写法

不同模型对指令的偏好差异很大。Mesh 不能只换 `model` 参数，还要换**提示词形态**。

| 维度 | Claude | GPT | Gemini | DeepSeek |
|---|---|---|---|---|
| 结构 | XML 标签清晰分层 | Markdown + 明确角色 | 自然语言 + 示例 | 简洁指令 + 代码上下文 |
| 约束 | 前置「必须/禁止」 | 后置 checklist | 示例优先 | 少而硬 |
| 长上下文 | 擅长，给足 | 给足但注意 lost-in-middle | 擅长 | 给足 |
| 输出 | 先计划后代码 | JSON schema 强约束 | 结构化 + 多模态 | 直接代码 |
| 温度 | 0.2–0.4 | 0.2 | 0.3 | 0.1–0.3 |

**Compiler 结构**：

```
[System 角色] + [项目宪法] + [Design DNA] + [App Graph 切片]
+ [任务模板] + [参考模式] + [输出 schema] + [自检清单]
```

- **项目宪法**：技术栈、命名、目录、禁止事项（如不得引入未批准依赖）。
- **图谱切片**：只注入当前任务相关的节点，避免上下文污染。
- **参考模式**：3–5 个真实界面的结构化摘要，不是原图。
- **自检清单**：让模型在输出前逐条检查（可显著降低 lint 问题）。

**缓存**：项目宪法、DNA、图谱切片做前缀缓存；相同前缀命中率目标 40%+。

## 7. 评估体系（Eval）

### 7.1 离线

- **UI Bench（自建）**：200 个真实需求 → 人工评分（视觉、层级、可用性、代码质量）。
- **Build Bench**：50 个生成工程 → 自动 `expo prebuild` + `tsc` + 单测，统计一次通过率。
- **Edit Bench**：100 个「把 X 改成 Y」的指令，统计 diff 正确率与回归率。
- **Design Lint Bench**：对比生成前后的 lint 问题数。

### 7.2 在线

| 指标 | 定义 | 目标 |
|---|---|---|
| 一次通过率 | 生成后无需修复即可构建 | > 85% |
| 采纳率 | 用户接受且 24h 未大改 | > 70% |
| 平均修复轮次 | 从生成到构建成功的迭代数 | < 1.8 |
| 成本 / 成功页面 | 总模型成本 ÷ 成功页面数 | < $0.35 |
| P95 首屏时间 | 从提交到可交互 | < 90s |

### 7.3 反事实日志

每次路由都记录**未选择的候选模型**及其预估分数。定期抽样，用备用模型重跑同一任务，比较真实结果。这样可以在不牺牲用户体验的情况下持续校准路由。

## 8. 成本控制

1. **预算上限**：项目级 /  workspace 级 / 日级三层；达到 80% 预警，100% 降级到省钱策略。
2. **前缀缓存**：系统提示、DNA、图谱切片。
3. **结果缓存**：相同「组件 + 指令 + DNA」在 24h 内复用。
4. **批量**：非交互任务（文案变体、商店图）走 batch API，成本降 50%。
5. **模型降级**：高频小改用 DeepSeek / Gemini Flash；只有困难任务升级。
6. **早停**：生成 3 页后让用户确认，避免一次性生成 30 页后全部重做。
7. **token 预算**：每个任务有 max_output；超限截断并提示，而不是无限重试。

**成本可视化**：工作室状态栏实时显示本次会话花费；项目页显示「每个页面/每次构建」的成本，让用户感知价值。

## 9. 安全与合规

- **密钥隔离**：供应商 key 只在网关侧，沙箱与前端不可见。
- **数据政策**：每个模型标注 `trainsOnData`；企业版可强制只用「不训练」的 API 或自托管。
- **地域**：中国版走 Qwen / DeepSeek / 国内合规通道；海外版走 Anthropic / OpenAI / Google。
- **PII**：进入模型前做实体识别与脱敏；日志默认不存完整 prompt，只存哈希与摘要。
- **出口限制**：Fable 5 等有出口限制的模型，按账号区域自动禁用，并在路由层过滤。
- **审计**：企业版记录「谁在什么时间用哪个模型生成了什么」，支持导出。

## 10. 一页总结

| 问题 | 答案 |
|---|---|
| 用户要选模型吗？ | 不需要。默认 Auto，可展开看「为什么选它」。 |
| 会不会被单一供应商绑架？ | 不会。注册表 + fallback + 自托管。 |
| 成本怎么控？ | 任务级路由 + 缓存 + 预算 + 早停。 |
| 质量怎么保证？ | 质量阈值 + 多模型评审 + 构建/ lint 闭环。 |
| 模型更新怎么办？ | 热更新注册表；每月 eval；每季度清理。 |
| 企业怎么信？ | 数据政策过滤、私有部署、审计日志、不训练承诺。 |
